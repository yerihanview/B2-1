# B2-1 평가 대비 설명 자료

병합된 프로그램을 설명하기 위한 자료다. 실제 실행 근거는 [최종 검토](final-review.md), [검수 기록](validation-results.md), [제출물 점검](submission-check.md)에 있다. 이 자료를 작성했다는 사실이 사용자의 이해도 평가 통과를 뜻하지는 않는다.

## 시작 설명 예시

> 이 프로그램은 Python 표준 라이브러리만 사용하는 CLI 가계부입니다. 거래·카테고리·예산을 JSONL로 저장하고 CSV로 교환합니다. CLI, 서비스, 저장소, 모델의 책임을 나누었고, 제너레이터로 거래를 읽으며 최신 K건은 bounded heap으로 고릅니다. 파일 변경은 잠금과 임시 파일 발행으로 보호하며, CSV는 모두 검증한 뒤 한 번 반영합니다. 보너스로 ZIP 백업, 월별 반복 내역, 한글 폭을 고려한 테이블 정렬과 저장 원자성을 구현했습니다. 개발 테스트와 별도로 명세 기반 CLI 검수를 실행했고, 최종 소스는 Python 3.10과 3.12에서 각각 117개 검수를 통과했습니다.

## 평가항목 1: 기능·영속성·입출력·오류

### 거래를 추가하면 프로그램 안에서 어떤 일이 일어나는가?

1. `python -m budget_app add`가 `__main__.py`에서 `cli.main`으로 진입한다.
2. CLI가 인자를 파싱하고 Repository의 session에서 잠금을 획득한다. 기존 데이터 전체를 검증한 뒤 누락된 기본 파일을 초기화한다.
3. 날짜·타입·카테고리·금액·메모·태그를 순서대로 입력받는다.
4. Service가 등록된 카테고리를 확인하고 새 UUID를 만든다. Transaction 모델이 실제 날짜, 양의 정수 금액, 메모·태그 규칙을 검사한다.
5. 기존 거래 generator와 새 거래를 연결하여 임시 파일로 기록한다. flush/fsync 후 원자적으로 발행한다.
6. 성공 ID를 표시하고 잠금을 정리한다. 잘못된 입력은 기존 거래를 바꾸지 않고 오류와 힌트로 끝난다. 최초 실행의 빈 파일 초기화는 별도 예외다.

근거: [CLI](../budget_app/cli.py), [Service.add](../budget_app/service.py), [Transaction](../budget_app/models.py), [Repository.session](../budget_app/repository.py).

### 재실행해도 데이터가 남는 이유는?

거래는 `transactions.jsonl`, 카테고리는 `categories.jsonl`, 예산은 `budgets.jsonl`에 저장한다. 매 명령이 새 프로세스라도 같은 `--data-dir` 파일을 읽으므로 상태가 이어진다. 기본 경로 `./data`는 현재 작업 디렉터리 기준이므로 다른 위치에서 실행한다면 같은 저장 폴더를 명시해야 한다. 반복 규칙을 등록한 경우에만 `recurring.jsonl`도 존재한다.

### CSV 오류 행은 어떻게 처리하는가?

헤더·인코딩·열 수·각 값과 카테고리를 확인하고 정상 후보를 디스크 staging에 쓴다. 검증 오류가 하나라도 있으면 거래 파일을 교체하지 않는다. 복구 가능한 행 오류는 최초 20건을 물리적 시작 줄 번호로 안내한다. 검증이 끝난 경우만 기존 거래와 후보를 합쳐 한 번 발행한다. 교체 이후 내구성 오류는 이미 반영되었을 수 있으므로 일반 검증 실패와 구분한다.

예시: 정상 1행 + 금액이 음수인 1행을 import하면 정상 행도 추가하지 않는다. [실행 로그](../evidence/bonus-core-demo.txt)에 원본 SHA-256 동일성 검사가 있다.

CSV에는 거래 ID와 반복 출처가 없다. 같은 CSV를 다시 import하면 새 거래로 추가되는 비멱등 동작이다. 전건 롤백은 프로젝트의 설계 선택이며 부분 성공 정책도 가능한 대안이다.

### 오류가 났을 때 사용자와 다른 프로그램은 어떻게 알아보는가?

stderr에 `[오류]`와 `[힌트]`를 출력하고 코드 2(입력), 3(파일·손상·내구성), 4(잠금 충돌)로 종료한다. 성공과 도움말은 0이다. traceback을 사용자에게 노출하지 않는다. `--help`와 인자 파싱 실패는 저장소를 열지 않는다.

## 평가항목 2: 모듈·클래스 책임·파일 안전성

### 왜 모듈과 클래스를 나누었는가?

| 책임 | 구현 | 분리 이유 |
|---|---|---|
| 입력·명령·출력 | cli.py | 저장 포맷과 사용자 화면을 분리 |
| 거래·예산·카테고리·반복 규칙 | Service | 도메인 규칙을 한곳에서 검증 |
| 파일 검증·잠금·원자 발행 | Repository | 모든 쓰기의 안전성 절차를 공통화 |
| 유효한 데이터 | Transaction, RecurringRule | 필드와 불변조건을 명시 |
| 외부 형식·표시 | csv_io, backup, formatting | CSV·ZIP·터미널 규칙을 분리 |
| 오류 공통 처리 | errors, decorators | 정상 흐름에 같은 오류 출력을 반복하지 않음 |

Service는 Repository를 생성자로 전달받는다. 이것이 의존성 주입(DI)이다. 실제 파일 저장소 대신 테스트용 메모리 저장소를 넣어 규칙을 검증할 수 있다. 모든 파일 작업이 자동으로 교체 가능한 완전한 플러그인 구조라는 뜻은 아니다.

### update/delete는 어떻게 원본을 보호하는가?

기존 파일을 직접 잘라 고치지 않는다. 같은 디렉터리 임시 파일에 변경된 전체 결과를 쓰고 flush/fsync한 뒤 `os.replace`로 교체한다. add도 같은 방식을 사용한다. 새 export/백업의 비덮어쓰기 발행은 배타적 hard link를 사용한다.

- 교체 전 실패: 기존 대상은 그대로이며 임시 파일을 정리한다.
- 발행 후 디렉터리 fsync/정리 실패: 변경은 반영됐다고 안내한다. 사용자가 미반영으로 오해해 무조건 재실행하지 않게 한다.
- 여러 파일을 하나로 묶은 트랜잭션이나 전원 차단까지 포함한 완전 내구성은 아니다.

읽기와 쓰기 모두 같은 배타 잠금 파일을 사용한다. 동시 접근을 거부하고 자신이 획득한 잠금만 정리한다. 강제 종료 후 남은 stale lock은 자동으로 지우지 않는다.

## 평가항목 3: 제너레이터·데코레이터·타입 힌트

### 최신순인데 어떻게 스트리밍할 수 있는가?

`Repository.iter_transactions`가 `yield`로 거래를 하나씩 제공한다. Service.select는 날짜와 파일 내 순서를 비교하는 최소 힙에 최신 K개만 유지하고 마지막에 K개만 정렬한다. 같은 날짜면 파일 뒤쪽 거래가 먼저다.

N개 거래에 대한 선택 알고리즘은 O(N log K), 선택용 추가 메모리는 O(K)다. 다만 전체 중복 ID·반복 출처 검증 집합은 O(N)이며 카테고리·월·규칙 집합도 별도 비용이다. **전체 명령 메모리가 O(K)라고 설명하면 안 된다.** 제너레이터는 거래 객체 전체를 목록으로 올리지 않는다는 이점이 있다.

### 데코레이터가 실제로 어디에 쓰였는가?

`cli.main`에 `@user_errors`를 적용했다. 명령의 정상 로직을 감싼 wrapper가 사용자 오류·입력 중단·파일 오류를 메시지와 종료 코드로 변환한다. `functools.wraps`로 원래 함수의 이름·메타데이터를 유지한다. 장식용 함수 정의만 둔 것이 아니라 실제 명령 진입점에 적용했다.

근거: [decorators.py](../budget_app/decorators.py), [cli.py](../budget_app/cli.py).

### 타입 힌트가 유효하지 않은 값을 자동으로 막는가?

아니다. `select(...) -> list[Transaction]`, `iter_transactions() -> Iterator[Transaction]` 같은 힌트는 호출·반환 계약을 읽기 쉽게 하고 정적 분석에 도움을 준다. 실제 잘못된 날짜·bool 금액·미등록 카테고리·손상 JSON은 런타임 검사로 막는다. `get_type_hints` 검사와 실제 잘못된 입력 테스트를 따로 실행했다.

## 평가항목 4: 포맷·10만 건·잘못된 CSV

### JSONL과 CSV 중 왜 JSONL을 내부 저장에 골랐는가?

JSONL은 한 줄에 객체 하나여서 줄 단위로 읽기 쉽고 태그 목록·선택 반복 출처를 표현하기 편하다. 반면 사람이 스프레드시트로 직접 편집하기는 불편하다. CSV는 외부 표 교환에 편하지만 헤더·열 순서·quoting·인코딩을 맞춰야 하고 태그 목록 표현도 별도 규칙이 필요하다. 따라서 내부 JSONL, 교환 CSV로 나누었다.

### 10만 건이면 어디가 병목이고 무엇을 바꾸겠는가?

모든 명령의 전체 무결성 검증, 조회 전체 스캔, 쓰기 전체 재작성이 병목이다. 기존 측정에서는 tracemalloc을 켠 10만 건 목록/검색이 약 11~12초, 추가가 약 20초, 수정이 약 15초였고 최대 Python 할당은 약 12MiB였다. 각 1회 관찰이며 프로세스 RSS나 일반 실행 속도와 다르다. 실제 수치·소스 SHA는 [측정 원본](../evidence/bonus-benchmark.jsonl)에 있다.

K=20과 1000의 전체 최대 메모리가 비슷한 것은 ID 검증 집합의 peak가 지배하기 때문이다. 이 측정만으로 힙의 O(K)를 증명하지 않는다. 개선안은 인덱스, 디스크 기반 중복 검증, SQLite 트랜잭션이다. 현재 미션에서는 저장 구조를 임의로 확장하지 않고 한계를 설명한다.

## 보너스 4개 설명

| 보너스 | 설명할 내용 | 실행·검수 위치 |
|---|---|---|
| 백업 | 같은 잠금 아래 원본 JSONL을 ZIP에 복사. manifest 크기/SHA-256 대조, 새 파일 배타 발행, 기존 백업 보존. 자동 restore 명령은 없음 | backup.py, test_bonus.py, bonus_smoke.py |
| 반복 내역 | 규칙과 생성 거래 출처 `(규칙 ID, 월)`로 중복 방지. 31일은 해당 월 말일로 보정. 수정해도 출처 유지. 거래 삭제 후 재실행하면 새 ID로 생성 | Service.apply_recurring, models.py, test_bonus_acceptance.py |
| 출력 정렬 | Unicode 폭을 계산하고 금액을 오른쪽 정렬. 제어문자는 출력 시 escape하고 원본 메모 보존. 복합 이모지는 터미널 차이 가능 | formatting.py, test_bonus_formatting.py |
| 원자성 강화 | 임시 파일·flush/fsync·원자 발행·실패 단계 구분을 기존/신규 쓰기 경로에 적용 | repository.py, 장애 주입 테스트 |

SHA-256 manifest는 원본과 백업 내용을 비교하는 수단이다. 서명된 진본 인증이나 자동 복구 기능을 뜻하지 않는다. 가상 폴더 복구 후 CLI로 읽는 검수는 별도로 수행했다.

## 코드 검토에서 실제로 고친 결함 설명

각각은 이미 수정·검수된 사례이며 현재 남은 오류 목록이 아니다.

- UUID를 강제로 충돌시킨 경우: 기존/후보 ID 집합 확인과 제한된 재생성, 고갈 시 원본 보존.
- 발행 뒤 정리 실패: 이미 반영된 사실을 오류 메시지에 포함.
- 깊은 JSON·순환 symlink: 사용자 traceback 대신 파일 오류로 안내.
- 유효한 대형 CSV 필드: 파서 기본 크기 제한을 조정하고 종료 시 복원.
- 큰 금액의 합계: 정상 입력 두 건의 합계가 Python 정수 문자열 제한을 넘는 경우 Decimal로 정확하게 출력. 입력 상한이나 전역 제한을 바꾸지 않았음.
