# 과잉 운영의 원인·재발 방지 지침·소스 재검토 설명

기준: `9c8fa85`. 이 문서와 [검토 원문](overengineering-review.md)은 사용자가 요청한 회고 기록이다. 새 개발 단계나 제출 필수물을 추가하는 규정은 아니다. 본문은 원인 분석과 적용 가능한 지침·변경안을 제시하며, 현재 AGENTS/spec/코드/기존 로그를 자동으로 변경·삭제하지 않는다.

## 1. 왜 과잉 운영으로 이어졌는가?

관찰 가능한 이력과 산출물을 근거로 한 분석이다. 단계별 실제 토큰 계측값은 없어 비용 비율이나 정확한 원인별 토큰 수로 표현하지 않는다.

| 빠져 있던 제약 | 실제로 한 선택 | 비용이 커진 이유 |
|---|---|---|
| 공식 요구·사용자 추가·개발자 선택의 구분 | 기존 내부 문서의 상세 정책까지 같은 무게의 완료 조건으로 취급 | 원문보다 엄격한 정책을 구현하고 검수하는 비용 발생 |
| 기록물의 범위와 보관 기준 | 실행 단계마다 결과 파일·검토 보고서를 추가 | 같은 결과를 여러 파일에 기록하고 상태·링크를 계속 동기화 |
| 검토 횟수와 추가 검토 사유 | 여러 역할이 단계별로 재검토 | 문맥 인계·동일 영역 재조회·결과 통합을 반복 |
| 완료 후 멈추는 기준 | 검수 이후에도 최종 보고·제출 점검 등 다음 유용한 작업을 계속 추가 | 완료 판정이 뒤로 이동하고 새 산출물이 다음 작업의 입력이 됨 |
| 위험별 검증 우선순위 | 일상 입력, 데이터 손실, 극단 입력을 비슷한 운영 절차로 다룸 | 작은 경계 수정에도 큰 재검토·기록 절차를 적용 |
| 사용량을 확인할 수 없을 때의 대체 예산 | 토큰 한도를 계측하지 못한 채 진행 | 에이전트 수·긴 재조회·출력량·문서 수 같은 관찰 가능한 비용도 제한하지 않음 |

기존 지침에도 “최소 기능”, “과도한 로그 금지”, “증거 최소화”는 있었다. 따라서 단순히 지침이 전혀 없었던 문제가 아니다. 그 원칙을 **새 파일을 언제 만들 수 있는지, 어느 결과를 한 번만 기록하는지, 무엇이 끝나면 멈추는지**로 구체화하지 못했고, 제가 개별 단계의 안전성과 설명 충실도를 우선하면서 전체 비용을 통제하지 못했다.

독립 검증과 보너스 전체 구현은 사용자가 요청한 범위였다. 그 요청을 역할별 문서 묶음·반복적인 완료 절차로 확장한 것은 제 운영 판단이다. 기존 지침이나 사용자의 승인에 책임을 돌릴 수 없다.

## 2. 재발 방지를 위한 지침안

아래는 향후 AGENTS에 반영하거나 작업 지시로 사용할 수 있는 지침이다. 현재 프로젝트 계약을 소리 없이 완화하는 효력은 없다.

1. **요구의 출처를 표시한다.** 작업 범위는 공식 필수, 사용자가 요청한 추가, 개발자가 제안한 선택으로 구분한다. 추가 입력 제한·동작 정책·외부 의존성은 근거와 비용을 설명한다. 편리한 구현을 위해 사용자에게 불필요한 제약을 만들지 않는다.
2. **계약의 기준 문서는 spec/design/acceptance로 둔다.** 실행·사용법·최신 검수 결과 요약은 README 한곳에 둔다. 짧은 운영 규칙은 AGENTS에 둔다. 추가 문서는 사용자 요청 또는 기존 문서로 수용할 수 없는 이유가 있을 때만 만든다.
3. **증빙 요구를 먼저 확인한다.** 원문이 요구한 결과를 보여준다. 별도 파일 형식이 요구되지 않으면 CI 기록과 필요한 대표 출력으로 충족한다. 매 실행의 로그를 저장소에 누적하거나 단계별 증거 묶음을 자동 생성하지 않는다.
4. **역할과 파일을 분리하되 보고서를 증식시키지 않는다.** 독립 검증자는 명세 기반 테스트·재현 결과를 담당하고 구현을 고치지 않는다. 개발자는 수정한다. 인계는 관련 파일·현재 SHA·실패 조건·다음 작업만 전달한다. 같은 영역의 추가 검토는 새 실패·변경·새 요구가 있을 때 수행한다.
5. **검증은 위험과 변경에 맞춘다.** 정상 흐름, 흔한 잘못된 입력, CSV 부분 반영, 원본 손실을 먼저 검증한다. 관련 검사로 수정 결과를 확인하고 기능 변경을 통합할 때 전체 회귀를 수행한다. 문서만 바뀌면 링크·내용을 검사하며 앱 전체 회귀·성능 측정을 불필요하게 반복하지 않는다.
6. **지원 환경 검증을 중복하지 않는다.** 기본 개발 환경과 CI의 최소 지원 버전을 활용한다. 여러 버전 전체 재실행은 호환성 우려·실제 실패·최종 검증 등 근거가 있을 때 한다. 이전 결과를 새 SHA의 실행 결과로 바꿔 적지 않는다.
7. **토큰 예산은 확인 가능한 범위로 관리한다.** 사용량 조회가 없으면 토큰 수를 지어내지 않는다. 필요한 부분만 읽고 요약을 인계하며 기본 검토 1회 후 추가 회차의 이유를 밝힌다. 예상 밖으로 범위가 커지면 새 보고서부터 만들지 말고 남은 필수 작업과 선택 작업을 짧게 정리한다.
8. **일상 위험과 극단 입력을 구분한다.** 실제 결함은 재현하고 최소 수정·회귀로 해결한다. 드문 사례의 작은 수정을 별도 프로젝트 단계로 확대하지 않는다. 현실적인 범위 제한이 필요하면 근거와 사용자 영향부터 제안한다.
9. **완료 조건을 고정한다.** 합의한 기능·필수 검수·README·필요한 CI가 충족되면 결과와 한계를 한 번 보고한다. 승인 후 다음 단계로 진행한다. 완료 후 설명자료·제출보고서·새로운 점검 단계를 스스로 추가하지 않는다. 사용자가 새로 요청하면 그 범위만 수행한다.
10. **비용 절감을 이유로 안전성과 사실성을 버리지 않는다.** 실제 재무 데이터 보호, 필수 검수, 고쳐진 결함의 회귀를 보존한다. 같은 결함 수정 최대 3회, 핵심 계약 변경·데이터 손실 위험·병합의 사용자 판단을 유지한다. 무실행·스킵·실패를 통과로 바꾸지 않는다.

사용 예시 지시:

> 공식 필수와 내가 요청한 추가 기능만 구현해. spec/design/acceptance를 기준으로 하고 결과는 README에 한 번 요약해. 별도 보고서나 evidence 파일은 먼저 필요성을 설명해. 검수자는 테스트와 재현 결과를 남기고 구현은 수정하지 마. 새 실패나 코드 변경이 없으면 같은 검토를 반복하지 마. 합의한 완료 조건을 충족하면 멈추고 결과와 한계를 보고해.

## 3. 소스 재검토 5개 항목

이 5개를 모두 삭제하라는 뜻은 아니다. 아래의 현재 동작, 추가된 목적, 실제 대가와 권고를 구분해 결정해야 한다. 특히 기존 spec과 테스트가 요구하는 동작을 바꾸려면 관련 계약도 함께 갱신해야 한다.

### 3.1 모든 데이터 명령의 전체 파일 검증

**현재:** [Repository.session](../budget_app/repository.py#L48)이 모든 데이터 명령에서 [validate](../budget_app/repository.py#L103)를 호출한다. 카테고리·예산·반복 규칙·거래를 모두 읽고 형식, 참조, ID·출처 중복을 확인한다. 따라서 `category list`도 거래 10만 건을 읽는다. 거래 조회와 직접 관련 없는 예산 파일이 손상되어도 목록 조회가 막힌다. 도움말과 인자 파싱 오류는 이 과정에 들어가지 않는다.

**왜 만들었나:** 어떤 명령에서도 손상을 놓치거나 손상 상태에서 파일을 바꾸지 않도록 강하게 보수적인 정책을 택했다.

**왜 재검토하나:** 원문은 입력 검증과 안전한 파일 처리를 요구하지만, 모든 조회가 모든 파일을 감사하라고 요구하지 않는다. 작은 조회도 데이터 전체 크기에 따라 느려지고, 서로 관련 없는 파일의 오류가 전파된다. 거래 ID·출처 집합도 메모리를 쓴다. 이후 select가 거래를 다시 읽는 등 반복 순회가 생긴다.

**더 작은 대안:** 명령이 필요로 하는 데이터와 변경 전 참조를 중심으로 검사 범위를 정한다.

| 명령 | 검사 범위의 예시 |
|---|---|
| category list | categories |
| list/search | transactions와 명세상 필요한 category 참조 |
| summary | transactions·budgets와 필요한 category 참조 |
| category remove | categories·transactions·recurring의 사용 여부 |
| backup | 스냅샷에 포함할 모든 저장 파일 |

이 표는 변경안이며 현재 계약은 아니다. 단순히 관련 없는 파일 검사를 줄여도 list/search는 최신 K건 선택을 위해 거래 전체를 읽는다. ID 중복 집합을 유지한다면 전체 메모리는 여전히 O(N)일 수 있다. 검사 범위를 줄였다고 전체 O(K)가 된다고 주장하면 안 된다.

**권고:** 소스 단순화의 우선 검토 대상이다. 조회 범위와 쓰기 전 안전성을 나누고, 어떤 손상을 해당 명령에서 발견하지 않게 되는지 명시한다. 원본 보존과 실제 필요한 참조 검사는 유지한다. add의 전체 파일 재작성도 관련 비용이지만, 이를 곧바로 직접 append로 바꾸는 것은 별도 안전성 판단이 필요하다.

### 3.2 카테고리·태그의 한글 금지

**현재:** [정규식](../budget_app/models.py#L12)이 영문·숫자·밑줄·하이픈만 허용한다. `food`는 되지만 `식비`, `교통비`는 거부한다. 입력과 CSV에 같은 정책을 적용하며 저장 파일의 한글 이름도 현재 계약상 손상으로 취급한다.

**왜 만들었나:** ASCII 허용 목록을 사용하면 이름의 문자 범위를 간단한 정규식으로 통일할 수 있다는 구현상의 편의가 있다. 이 정책은 제가 인수하기 전 spec에도 있었지만, 한글을 금지해야 하는 사용자 요구 근거는 원문에서 확인하지 못했다.

**왜 재검토하나:** 원문은 등록된 category 사용을 요구할 뿐 영어 이름만 요구하지 않는다. UTF-8 JSONL과 CSV는 한글을 저장할 수 있으므로 저장 기술의 한계도 아니다. 한국어 가계부의 사용성을 불필요하게 제한한다.

**대안:** 앞뒤 공백을 정리한 비어 있지 않은 Unicode 문자열을 기본으로 하고, 줄바꿈·제어문자 등 실제 출력·데이터 계약에 문제가 되는 문자만 제한한다. 내부 공백·길이·대소문자 정책은 사용자 관점에서 정한다. Unicode 이름을 일괄 정규화·변환하면 이름 충돌이 생길 수 있으므로 자동 마이그레이션하지 않는다.

**권고:** 한글 허용을 우선 고려한다. 기존 영문 이름은 그대로 사용할 수 있게 하고 CLI·CSV·저장 파일 검증·검색을 일관되게 바꿔야 한다. 카테고리 선등록, 중복 처리, 사용 중 삭제 거부는 그대로 유지한다.

### 3.3 조회 1000건 상한·CSV BOM 거부 등의 추가 제한

이 항목은 둘 이상의 입력 정책을 묶어 지칭한 것이다.

**조회 상한:** 현재 [CLI](../budget_app/cli.py#L44)와 [Service.select](../budget_app/service.py#L166)는 `list --limit 2000`을 오류로 처리한다. 원문은 기본값이 있는 limit 지원을 요구하지만 최대 1000을 정하지 않았다. 선택 알고리즘도 1000이라는 숫자에 의존하지 않는다. 사용자가 K를 늘리면 힙 메모리와 출력량이 늘어난다는 자원 비용이 있을 뿐이다.

권고안은 기본 20과 양의 정수 검증을 유지하고 임의의 1000 상한을 제거하거나, 상한이 꼭 필요한 운영 근거를 정하는 것이다. 무제한 전체 출력을 기본값으로 바꾸자는 제안은 아니다. 변경 시 CLI와 Service 양쪽의 검사·도움말·spec·경계 테스트를 함께 맞춰야 한다.

**BOM 거부:** 일부 도구는 UTF-8 CSV 앞에 BOM 바이트 `EF BB BF`를 붙인다. 화면에는 첫 컬럼이 date로 보여도, 현재 [CSV 읽기](../budget_app/csv_io.py#L30)는 첫 헤더를 `\ufeffdate`로 읽어 스키마 불일치로 거부한다. BOM은 UTF-8 텍스트 앞의 식별 표식이며 원문에는 BOM 금지 규정이 없다.

권고안은 import에서 `utf-8-sig`로 읽어 BOM이 있는 UTF-8과 없는 UTF-8을 둘 다 받는 것이다. export는 현재처럼 BOM 없는 UTF-8로 유지할 수 있다. 컬럼 이름·순서·타입 검사, 잘못된 인코딩 오류, CSV 전건 미반영은 유지한다. 임의의 인코딩 추측이나 자동 문자 치환까지 추가할 필요는 없다.

**그 밖의 제한:** memo 500자, category/tag 길이, summary top 최대 100도 프로젝트가 정한 범위다. 모두 무조건 없애기보다 실제 자원·사용성 근거가 있는지 확인한다. 근거 없는 제한을 추가한 뒤 그것을 필수 평가요건으로 다루지 않는다.

**권고:** 한글 허용과 함께 사용자 편의에 직접 영향을 주므로 우선 검토한다. 기존 테스트가 제한 거부를 기대하므로 테스트만 삭제하지 말고 새 계약과 정상·오류 사례로 교체해야 한다.

### 3.4 백업 manifest·해시 검증

**현재:** [create_backup](../budget_app/backup.py#L15)은 JSONL을 ZIP에 넣으면서 파일별 크기와 SHA-256을 계산하고 manifest.json에 저장한다. 기본 3파일과 존재하는 규칙 파일을 담고, 타임스탬프와 UUID가 있는 새 이름으로 발행한다. 테스트와 데모는 해시·원본 바이트를 대조하고 가상 복구까지 검증한다.

**원문 최소 요구:** 타임스탬프가 포함된 백업 파일 생성이다. ZIP 형식·manifest·SHA-256은 추가 설계다. 다만 사용자가 보너스 전체를 요구했으므로 백업 기능 자체는 유지해야 한다.

**추가한 이점과 대가:** 백업이 원본과 같은지 대조할 수 있다. 그 대신 ZIP 내부 형식·manifest 구조·해시 검수까지 유지할 계약이 늘었다. SHA-256은 내용 비교 수단이지 서명된 진본 인증이나 자동 복구 기능은 아니다.

**작은 대안:** 같은 잠금 아래 기본 저장 파일을 타임스탬프가 있는 ZIP에 담고, 원본과 백업 비교는 테스트에서만 수행할 수 있다. 생성되는 manifest를 없애도 이름·원본 보존·일관된 스냅샷·기존 백업 비덮어쓰기·발행 전후 오류 구분은 유지할 수 있다.

**권고:** 현재 백업 모듈은 43줄로 크지 않다. 이미 유효한 백업 형식과 테스트를 바꾸는 비용까지 고려하면 앞선 세 항목보다 우선순위가 낮다. 현재 구현은 유지하고, 이후 작은 과제에서는 manifest를 기본으로 추가하지 않는 선택도 합리적이다. 제거한다면 기존 ZIP의 해석과 복구 안내에 미치는 영향도 확인해야 한다.

### 3.5 4300자리 금액·UUID 충돌 등의 드문 경계 처리

**현재:** 아주 큰 정상 금액 두 건의 합계를 출력할 때 Python의 정수 문자열 제한을 넘어 traceback이 나는 실제 결함이 있었다. Decimal의 정확한 출력·자리수 계산으로 고쳤다. [allocate_id](../budget_app/service.py#L19)는 기존 ID와 충돌하면 제한된 횟수만 재생성하고 고갈 시 미반영 오류로 끝낸다. 깊은 JSON·순환 링크·발행 후 정리 실패도 사용자용 오류로 처리한다.

**왜 검수했나:** ID 유일성, traceback 없는 오류, 원본 보존과 연결된다. 발생 확률이 낮아도 실제 결함으로 재현된 경우 수정할 이유가 있다.

**과했던 부분:** 작은 코드 수정에 여러 에이전트의 반복 검토, 여러 Python 실행·보고서·단계별 증빙을 덧붙였다. 이미 해결한 결함의 회귀를 남기는 것과, 그 사례를 별도 프로젝트 단계로 확대하는 것은 구분해야 한다.

**권고:** 작고 실제로 유효한 수정은 유지한다. 예산을 줄이려고 다시 traceback이 나게 만들거나 UUID 유일성 검사를 없애지 않는다. 일상 입력·CSV 부분 실패·파일 손실 같은 위험을 우선 검수하고, 드문 경계는 재현→최소 수정→해당 회귀→필요한 통합 검증으로 마무리한다. 금액 지원 범위를 정하고 싶다면 별도 사용성 계약으로 결정하며, 테스트를 쉽게 만들기 위해 임의로 작은 상한을 넣지 않는다.

## 4. 이 문제를 해결하는 순서 제안

1. 불필요한 문서·과거 로그를 현재 브랜치에서 통합·정리한다. Git 이력의 과거 기록은 보존한다. 공식 요구·사용자 요청·개발자 선택을 구분한다.
2. 한글 이름·불필요한 limit 상한·BOM 거부를 먼저 결정한다. 사용자 편익이 분명하고 저장소 전체 구조를 바꾸지 않는 항목이다.
3. 명령별 검증 범위를 설계한다. 원본 보호와 참조 무결성의 어떤 약속이 바뀌는지 확인한 뒤 구현한다.
4. 백업 manifest와 이미 수정된 드문 경계 처리는 절감 효과·변경 위험을 비교해 유지 여부를 판단한다.

이번 요청에서는 검토 원문 보존과 원인·지침·상세 설명까지만 수행한다. 실제 코드·계약 완화·기존 자료 삭제는 별도 실행 작업이다. 이 순서를 수행하기 위해 다시 역할별 보고서나 증거 묶음을 만들 필요는 없다.
