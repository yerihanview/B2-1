# 과잉 운영 검토 원문

검토 기준: `9c8fa857542d7d78ef01f614164d11ed5d2b6a20`. 아래는 사용자에게 전달한 검토 본문을 그대로 옮긴 것이다. 파일 링크만 GitHub에서 열리도록 상대 경로로 바꿨다. 수치는 이 문서를 추가하기 전 기준이다. 원인·재발 방지 지침·소스 5개 항목의 상세 설명은 [후속 설명](overengineering-followup.md)에 있다.

---

점검 결과, **개발 프로세스와 기록물은 미션 규모에 비해 과했습니다.** 소스의 기본 구조는 적절하지만, 원문보다 엄격하게 만든 정책 중 줄일 여지가 있습니다. 제가 완료 기준과 기록 범위를 더 작게 잡았어야 했습니다.

이번 점검에서는 파일을 변경하거나 새로운 보고서 파일을 만들지 않았습니다.

**1. 토큰이 많이 소비된 지점**

정확한 총토큰과 단계별 사용량을 조회하는 기능은 현재 제공되지 않습니다. 따라서 “어디에 몇 % 썼다”는 수치는 확인할 수 없습니다. 대신 대화와 변경 이력에서 다음 낭비 패턴을 확인했습니다.

| 지점 | 비용을 키운 방식 |
|---|---|
| 여러 에이전트의 반복 검토 | 설계·구현·보너스·최종 검토 때 문맥 전달, 결과 보고, 통합 판단을 반복 |
| 긴 문서·코드 재조회 | 이미 확인한 문서와 소스를 여러 단계에서 다시 읽음 |
| 단계별 기록물 생성 | 검수 결과를 로그·검토 보고서·제출 점검표에 중복 작성 |
| 반복적인 완료 절차 | 구현 완료 이후 최종 검토, 데모 정리, 제출 점검을 별도 작업으로 계속 확장 |
| 환경 문제 대응 | 게시 오류 상태 재조회와 안내가 길어짐 |

테스트 실행 시간 자체가 토큰은 아닙니다. **결과를 읽고 분석하고 설명하고 문서를 갱신하는 반복**에서 토큰이 늘어났습니다.

특히 인수 이후 변경 이력은 앱·테스트·도구 관련 커밋 4개에 비해 문서·프로세스 관련 커밋이 6개였습니다. 커밋 수가 토큰 사용량을 뜻하지는 않지만, 부가 작업의 비중을 보여줍니다.

**2. 중간 산출물은 대부분 별도 파일일 필요가 없었습니다**

실제 규모는 다음과 같습니다. 줄 수에는 주석과 빈 줄도 포함됩니다.

| 구분 | 파일 수 | 줄 수 |
|---|---:|---:|
| 앱 코드 | 11 | 1,250 |
| 테스트 | 9 | 1,929 |
| 개발용 스크립트 | 3 | 297 |
| docs 문서 | 13 | 958 |
| evidence | 12 | 764 |
| README·AGENTS | 2 | 209 |

제가 처음 인수한 `8ccbc22` 시점에도 docs는 이미 **8개·445줄** 있었습니다. 이후 제가 **13개·958줄**로 늘렸습니다.

설계·명세·검수 기준을 분리하는 것은 유효합니다. 다만 다음 기록들은 상당 부분 통합할 수 있었습니다.

- `handover-review`: PR 설명이나 이슈 기록으로 충분
- `validation-results`, `final-review`, `submission-check`: 하나의 결과 요약으로 통합 가능
- `implementation-plan`, `failure-policy`: 짧은 AGENTS 규칙으로 통합 가능
- `learning-map`, `evaluation-guide`, `demo`: 학습 설명 자료 하나로 통합 가능

독립 검증은 사용자가 요청한 유효한 운영 방식입니다. **역할을 분리한다고 해서 역할마다 별도 계획서·보고서·로그 묶음을 만들 필요는 없었습니다.**

**3. evidence는 공식 필수 제출물이 아니었습니다**

첨부한 공식 원문 텍스트를 다시 확인했습니다.

- 필수 README 내용은 명시되어 있습니다.
- 기능 동작과 설계 이유를 확인하는 평가항목이 있습니다.
- **별도 evidence 폴더, 단계별 테스트 로그 파일, 스크린샷 장수는 요구하지 않습니다.**
- 10만 건 항목도 병목과 개선 방법을 설명하는 요구입니다. 실제 벤치마크 파일 제출까지 강제하지 않습니다.

현재 evidence 764줄 중 **408줄은 이전 단계의 전체 테스트 로그 4개**입니다. 당시 결과로는 유효하지만, 최신 제출물에 계속 보관할 필요는 낮습니다. 기본 CLI 데모 로그도 여러 버전으로 중복되어 있습니다.

이것은 제가 **개발 과정의 추적 기록을 제출 증빙 수준으로 확대해 보관한 것**입니다. 검수를 실제로 수행한 것은 유용했지만, 결과를 모두 파일로 남기는 선택은 과했습니다.

이 미션에는 다음 정도면 충분합니다.

- 재현 가능한 테스트
- GitHub Actions 실행 결과
- README의 최신 검증 요약
- 평가에서 필요할 때 보여줄 대표 실행 결과

`evidence/`는 공식 요건 때문에 유지해야 하는 폴더가 아닙니다.

**4. 소스에서 과한 부분과 유지할 부분**

1,250줄이라는 규모만으로 과잉 구현이라고 판단하기는 어렵습니다. 기본 기능에 보너스 4개까지 포함했고, 프레임워크·DB·복잡한 상속 체계도 없습니다. 다만 다음 추가 정책은 재검토할 가치가 있습니다.

| 항목 | 판단 |
|---|---|
| **모든 데이터 명령에서 모든 파일 전체 검증** | 축소 검토 1순위. 카테고리 목록 조회에도 거래 전체를 검사합니다. 미션 필수 요구를 넘어선 정책이며 스캔·메모리 비용과 결합도를 늘립니다. |
| **카테고리·태그 한글 금지** | 원문 요구가 아닙니다. 현재 `식비` 같은 이름을 거부해 사용성을 제한합니다. 인수 전 spec부터 있던 추가 제약입니다. |
| **조회 최대 1000건·CSV BOM 거부 등** | 원문에 없는 추가 제한입니다. 필요성과 사용자 편의를 다시 판단해야 합니다. |
| **백업 manifest·해시 검증** | 원문 최소 요구보다 확장됐습니다. 다만 백업 모듈 자체는 43줄로, 현재 복잡도의 큰 원인은 아닙니다. |
| **4300자리 금액·드문 UUID 충돌 등 경계 처리** | 수정 자체는 작고 실제 결함을 해결했습니다. 이를 다루는 검토·보고 절차에 들인 비용은 과했습니다. |

전체 파일 검증은 [Repository.session](../budget_app/repository.py#L48), 한글 제한은 [models.py](../budget_app/models.py#L12), 조회 상한은 [cli.py](../budget_app/cli.py#L44)에서 확인했습니다.

반면 다음은 유지하는 것이 타당합니다.

- CLI·서비스·저장소·모델의 책임 분리
- 제너레이터와 최신 K건 선택
- 입력 검증과 사용자용 오류 처리
- 임시 파일을 통한 안전한 교체
- CSV 오류 시 전건 미반영
- 반복 거래의 같은 월 중복 생성 방지

테스트 117개도 개수만으로 과하다고 볼 수는 없습니다. **중복 검수는 조정하되, 실제 결함을 잡은 회귀 테스트를 단순히 개수를 줄이려고 삭제하면 안 됩니다.**

제가 권장하는 정리 방향은 **README + 짧은 AGENTS + spec/design/acceptance + 코드·테스트·CI**를 중심으로 두고, 중복 보고서와 과거 evidence를 main에서 정리하는 것입니다. 이력은 Git에 남습니다. 소스는 전체를 다시 개발하기보다, 전체 파일 검증 범위와 불필요한 입력 제한부터 검토하는 편이 비용 대비 효과가 큽니다.

이번 과소비의 주된 원인은 **문서·검토·완료 절차를 계속 확장하고 같은 결과를 여러 곳에 기록한 운영 방식**으로 판단합니다.
