## 최종 검토 중 수정한 결함

- 대상 A04/A06/T04/T12. 정상 입력으로 저장되는 4300자리 양의 정수 지출 2건의 합계가 4301자리가 되면 summary에서 Python 정수→문자열 변환 제한으로 traceback이 발생했다. 예산 유무 양쪽에서 독립 CLI 실패 테스트로 재현했다.
- 입력 상한을 새로 만들거나 전역 변환 제한을 해제하지 않고, Decimal의 정확한 정수 출력과 자리수 계산으로 해결했다. 수정 1회 후 두 Python 버전에서 기대값을 유지한 채 통과했다.
- 별도 읽기 전용 검토자가 예산 없음/1/4300자리 예산, 정확한 합계·음수 잔액·TOP, 일반 사용률·HALF_UP·예산 동일/초과 경계, 원본 보존·잠금 정리·전역 설정 보존을 재검증했다. 그 범위에서 추가 코드 결함은 발견하지 못했다.

## 평가에서 설명할 핵심

1. CLI는 입력/출력, Service는 거래 규칙과 흐름, Repository는 파일·검증·잠금을 소유한다. 생성자 DI로 저장소를 테스트에서 바꿀 수 있다.
2. Transaction dataclass와 타입 힌트는 계약을 드러내고, 실제 입력/손상 데이터 검증은 런타임 검사로 수행한다.
3. generator는 거래를 한 줄씩 읽고 bounded heap은 최신 K개만 유지한다. ID·반복 출처 중복 검증 집합 때문에 전체 메모리는 O(N)이며 전체 O(K)를 주장하지 않는다.
4. 임시 파일 완성 후 flush/fsync·원자적 발행으로 교체 전 실패에서 원본을 보존한다. 단일 파일 원자성이며 다중 파일 트랜잭션이나 전원 장애 완전 내구성은 아니다.
5. CSV staging은 전건 검증 후 한 번 반영한다. user_errors decorator가 실제 CLI 경계에서 오류 메시지와 종료 코드를 공통 처리한다.
6. JSONL은 복합 태그와 스트리밍에 편리하고 CSV는 외부 표 교환에 편리하다. 10만 건에서는 전체 검증·스캔·재작성이 병목이며 인덱스/디스크 검증/SQLite가 개선 대안이다.

## 승인 전에 알아둘 한계

- delete는 확인 프롬프트와 자동 복구가 없다. backup은 제공하지만 자동 restore 명령은 없다.
- CSV 재수입은 중복 추가다. 반복 거래는 명시적인 apply 명령으로 생성하고 백그라운드에서 실행하지 않는다.
- 읽기에도 잠금을 사용한다. 강제 종료 후 stale lock은 사람의 확인이 필요하다. 교체 후 오류는 반영됐을 수 있어 무조건 재실행하면 안 된다.
- 실제 검증 플랫폼은 Linux와 Python 3.10/3.12이며 모든 파일시스템·전원 차단 상황을 보증하지 않는다. 복합 이모지 폭은 터미널에 따라 다르다.
- main 보호 규칙 조회는 GitHub integration 권한 403으로 확인하지 못했다. 조회 가능한 repository ruleset 목록은 비어 있었다. 따라서 CI 실패 시 병합을 기술적으로 차단한다고 주장하지 않는다. 보호 설정은 변경하지 않았다.
- 클라우드 환경 게시 오류는 별도 미해결 사항이다. 현재 GitHub 작업과 PR/CI는 동작하며 코드·증거는 GitHub에 보존된다.

## 남은 사용자 판단
